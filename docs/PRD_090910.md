## 0. Claude Code에게 (먼저 읽을 것)

- 이 문서는 3일짜리 인턴십 과제의 단일 진실 원천이다. 여기 없는 기능은 만들지 않는다.

- 우선순위는 트랙별 **P0 → P1 → P2** 순이며, 일정이 밀리면 P2부터 버린다. §3.3 확장 계획은 P2까지 끝난 뒤에만 착수한다.

- LLM 호출은 반드시 `LlmProvider` 인터페이스 뒤에 숨긴다. 실제 모델은 사내 로컬 LLM 두 종(gemma4, qwen3)이며 둘 다 **OpenAI 호환 API**(`/v1/chat/completions`)로 노출된다(§F2). **`MockLlmProvider`를 먼저 만들고**, 2일차 후반에 `OpenAiCompatProvider` 하나로 두 모델을 모두 붙인다. 모델별 클래스를 따로 만들지 않는다.
- 각 작업 단위가 끝나면 빌드·테스트가 통과하는 상태로 커밋한다. 커밋 메시지는 Conventional Commits(`feat:`, `fix:`, `chore:`).

## 1. 개요

### 1.1 문제
개발자는 매일 업무 일지를 써야 하지만, 하루 동안 무엇을 했는지 커밋·PR·미커밋 작업·계획을 다시 뒤져서 정리하는 데 시간이 든다. 커밋을 안 한 작업이나 "계획만 세운 것"은 기록에서 누락되기 쉽다.

### 1.2 해결
GitHub 활동(커밋·PR·머지)과 VS Code 안의 미커밋 작업(로컬 diff, TODO, 편집 세션)을 자동 수집하고, LLM으로 사람이 읽을 수 있는 문장으로 해석해 **업무 일지 초안**을 만들어 준다. 결과는 웹 대시보드에서 조회·편집하고, Mattermost로 알림·요약을 보낸다.

### 1.3 산출물
1. **웹 대시보드** (React) — 일별/인원별/리포지터리별 조회, 일지 초안 편집·확정
2. **백엔드 API 서버** (Spring Boot) — 수집·저장·LLM 해석·알림
3. **VS Code 확장** (TypeScript) — 작업 수집기 클라이언트 (`.vsix` 파일)

### 1.4 사용자
- **개발자(1차 사용자)**: 자기 일지 초안을 받고, 수정 후 확정한다.
- **팀 리드/PM(2차)**: 팀원별·리포별 활동을 대시보드로 본다.

## 2. 역할 분담

2인 팀. 각자 **자기 트랙 안에서 프론트+백엔드를 수직으로** 맡는다(기능 단위로 나누고 레이어로 나누지 않는다). 공통 기반은 1일차 오전에 함께 세팅한 뒤 갈라진다.

| 담당 | 트랙 | 소유 영역 |
|------|------|---------|
| **담당자 1 — 클라이언트** | 대시보드, VS Code 확장, 클라이언트 산출물 | `frontend/` 전체, `vscode-extension/` 전체, `backend/.../vscode/`(세션 수신 API), `backend/.../draft/` 중 초안 CRUD·편집·확정 API |
| **담당자 2 — 연동** | GitHub 연동, LLM 해석, Mattermost·외부 API | `backend/.../auth/`, `github/`, `activity/`, `llm/`, `draft/` 중 `DraftGenerator`, `notify/`, `external/` |
| **공통(1일차 오전)** | 기반 | 모노레포 스캐폴딩, `docker-compose.yml`, Flyway V1 스키마, §7 API 계약 확정, 목업 JSON 스키마 합의 |

**인터페이스 계약 규칙**: 두 트랙이 만나는 지점은 §7 API 명세와 §6 스키마뿐이다. 계약을 바꿔야 하면 PRD를 먼저 고치고 상대에게 알린 뒤 코드를 바꾼다. 담당자 1은 담당자 2의 API가 나오기 전까지 목업(`VITE_USE_MOCK=true`)으로 진행하고, 담당자 2는 프론트 없이 `curl`/HTTP 파일로 API를 검증한다.

**컨플릭트 방지**: `backend/.../draft/` 패키지는 두 사람이 겹치는 유일한 곳이다. 담당자 2가 `DraftGenerator`(생성 로직·템플릿·스케줄러)를, 담당자 1이 `DraftController`+`DraftService`의 조회·수정·확정을 맡는다. `Draft` 엔티티 자체는 1일차 오전 공통 작업으로 확정하고 이후 변경은 합의 후에만.

## 5. 기능 상세

### F1. GitHub 연동 (P0, 담당자 2)

**목적**: 등록된 리포의 커밋·PR·머지 이력을 DB에 정규화해 저장한다.

**동작**
1. 사용자가 대시보드에서 리포를 등록한다 (`owner/repo`). 사용자의 OAuth 토큰으로 접근 가능한 리포만 등록 가능.
2. `GitHubCollector`가 10분마다 (`@Scheduled`) 각 리포에 대해:
   - `GET /repos/{o}/{r}/commits?since={lastSyncedAt}` → 커밋 목록
   - 각 커밋 `GET /repos/{o}/{r}/commits/{sha}` → 변경 파일·patch (diff)
   - `GET /repos/{o}/{r}/pulls?state=all&sort=updated` → PR 및 머지 여부
3. 결과를 `activity` 테이블에 `type = COMMIT | PR_OPENED | PR_MERGED` 로 저장. 동일 `(repo_id, external_id)`는 중복 저장하지 않는다(UPSERT).
4. diff는 파일당 최대 200줄, 커밋당 최대 3,000자로 잘라 `raw_diff`에 저장한다(LLM 토큰 절약).
5. 수동 동기화 버튼 (`POST /api/repos/{id}/sync`) 제공.

**수용 기준**
- 리포 등록 후 수동 동기화 시 최근 7일 커밋이 조회된다.
- 같은 커밋을 두 번 동기화해도 row가 늘지 않는다.
- author의 GitHub login이 `user` 테이블과 매핑된다(미가입자는 `external_login`만 저장).

### F2. LLM 해석 (P0, 담당자 2)

**목적**: 커밋 메시지 + diff를 "무엇을, 왜, 어떤 영향" 형태의 한국어 2~3문장 요약으로 바꾼다.

**인터페이스**
```java
public interface LlmProvider {
    String id();                              // "mock" | "gemma4" | "qwen3"  (프리셋 이름)
    String complete(LlmRequest req);          // system + user prompt → text
}
```
- 프로바이더 선택: `application.yml`의 `worklog.llm.provider` 값 (기본 `mock`, 실서비스 기본 `gemma4`). P2에서 대시보드 설정으로 사용자별 오버라이드.
- **사내 로컬 LLM 프리셋** (둘 다 OpenAI 호환 API — `GET {baseUrl}/models`, `POST {baseUrl}/chat/completions`):

  | 프리셋 | baseUrl | model | 용도 |
  |---|---|---|---|
  | `gemma4` | `http://61.32.164.99:18000/v1` | `google/gemma-4-26b-a4b-qat` | **기본**. 커밋 요약·초안 생성 |
  | `qwen3` | `http://agent.uxis.co.kr:11435/v1` | `qwen3.8:27b` | 대체/비교용. 설정에서 전환 |

  구현체는 `OpenAiCompatProvider` 하나이고 프리셋은 `application.yml`의 `worklog.llm.presets` 맵으로 정의한다. 새 모델을 붙이는 일은 코드 수정 없이 프리셋 추가로 끝나야 한다.
  ```yaml
  worklog:
    llm:
      provider: ${WORKLOG_LLM_PROVIDER:mock}
      presets:
        gemma4: { base-url: "http://61.32.164.99:18000/v1", model: "google/gemma-4-26b-a4b-qat", api-key: "${GEMMA4_API_KEY:}" }
        qwen3:  { base-url: "http://agent.uxis.co.kr:11435/v1", model: "qwen3.8:27b", api-key: "${QWEN3_API_KEY:}" }
  ```
  요청 파라미터: `temperature 0.2`, `max_tokens 400`, `stream false`. qwen3는 thinking 출력이 섞일 수 있으므로 응답에서 `<think>...</think>` 블록을 제거한 뒤 저장한다. 타임아웃 기본 60초, 프리셋별로 `timeout-seconds` 로 조정한다 — `qwen3.8:27b` 는 3,000자 diff 한 건에 실측 51초가 걸려 60초로는 큰 커밋이 매번 실패하므로 180초를 쓴다. 또한 ollama 계열 엔드포인트는 JSON 을 `application/octet-stream` 으로 내려보내므로 선언된 콘텐츠 타입을 믿지 않고 JSON 으로 읽는다.
- 기동 시 선택된 프리셋의 `/models`를 한 번 호출해 연결·모델명을 검증하고, 실패하면 경고 로그 후 `mock`으로 폴백한다(서비스는 뜨게).
- `MockLlmProvider`: 커밋 메시지를 그대로 "`{메시지}` 작업을 수행했습니다. (변경 파일 N개)" 로 반환. 1일차 통합에 사용.
- 실제 프로바이더 구현체는 HTTP 호출만 담당. 프롬프트는 `llm/prompts/` 아래 텍스트 파일로 분리.
- 결과는 `activity.summary`에 캐시하고, `summary`가 이미 있으면 재호출하지 않는다.
- 실패 시 예외를 삼키고 `summary = null`, `summary_status = FAILED` 로 두고 다음 스케줄에 재시도(최대 3회).

**프롬프트 (커밋 요약)**
```
[system]
당신은 개발팀의 업무 일지 작성 보조자입니다. 주어진 커밋 메시지와 diff를 보고
한국어로 2~3문장, 다음 형식으로 요약하세요: (1) 무엇을 변경했는지 (2) 왜/어떤 효과인지.
파일명이나 함수명은 필요할 때만 언급합니다. 추측하지 말고 diff에 근거하세요.

[user]
리포: {repo}
커밋 메시지: {message}
변경 파일: {files}
diff:
{diff}
```

**수용 기준**
- `provider=mock`일 때 커밋 동기화 직후 모든 activity에 summary가 채워진다.
- 프로바이더를 `gemma4` 또는 `qwen3`로 바꾸고 재시작하면 코드 수정 없이 실제 요약이 나온다.

### F3. 일지 초안 생성 (P0 — 생성 로직 F3a: 담당자 2 / CRUD·확정 API F3b: 담당자 1)

**목적**: 특정 사용자·날짜의 활동을 묶어 업무 일지 초안 1건을 만든다.

**트리거**
- 수동: 대시보드 "초안 생성" 버튼 (`POST /api/drafts/generate?date=&userId=`)
- 자동: 매일 18:00 KST 스케줄러가 전 사용자에 대해 생성 (설정으로 시각 변경)

**입력**: 해당 날짜(KST 기준 00:00~23:59)의 activity(COMMIT/PR/MERGE) + VS Code 세션(F6, 있으면).

**출력 템플릿 (Markdown, 고정)**
```
# {YYYY-MM-DD} 업무 일지 — {이름}

## 완료한 작업
- [{repo}] {summary}  (commit abc1234)
- [{repo}] PR #12 머지: {제목}

## 진행 중 / 미커밋
- [{repo}] {vscode 세션 요약 또는 변경 파일 목록}

## 계획 / TODO
- {코드 내 TODO 주석 또는 VS Code에 기록한 계획}

## 메모
(직접 작성)
```
- 활동이 0건이면 초안을 만들지 않고 `204`.
- 초안은 `draft` 테이블에 `status = DRAFT`로 저장, 사용자가 편집 후 `CONFIRMED`로 바꾼다.
- 같은 사용자·날짜에 초안이 이미 있으면 **재생성 시 덮어쓰지 않고** 새 버전(`version+1`)을 만든다. 확정본은 재생성 대상에서 제외.

**수용 기준**
- 커밋 3개가 있는 날짜에 초안을 생성하면 "완료한 작업"에 3줄이 들어간다.
- 초안 편집 후 확정하면 상태가 바뀌고 자동 스케줄러가 덮어쓰지 않는다.

### F5. 인증 (P0, 담당자 2)

- 웹: GitHub OAuth (scope: `read:user repo`) → 서버가 사용자 upsert 후 JWT(HS256, 12h) 발급. 프론트는 `Authorization: Bearer`.
- GitHub access token은 서버 DB에 암호화(AES) 저장, 수집기에서 사용.
- VS Code 확장·외부 API: `/settings`에서 발급한 개인 API Key (`X-Api-Key` 헤더). 키는 해시로 저장, 발급 시 1회만 평문 노출.
- 권한: 본인 초안만 편집 가능. 조회는 같은 서비스 내 전원 가능(단일 팀 전제).

### F6. VS Code 확장 — 작업 수집기 (P0, 담당자 1)

**목적**: 커밋되지 않은 작업과 계획을 놓치지 않고 백엔드로 보낸다.

**수집 항목**
1. **미커밋 변경**: 워크스페이스의 `git status --porcelain` + `git diff` (스테이지 포함). 파일별 추가/삭제 줄 수, diff 텍스트(파일당 200줄 제한).
2. **현재 브랜치·리포 원격 URL** → 서버의 `repo`와 매핑.
3. **TODO 주석**: 변경된 파일 안의 `TODO:`, `FIXME:` 라인.
4. **작업 계획 메모**: 명령 팔레트 `WorkLog: 오늘 계획 기록` → 입력창에 적은 텍스트.
5. **편집 세션**: 파일 저장 이벤트를 세어 "몇 시부터 몇 시까지 어떤 파일을 만졌는지" (파일 경로 + 최초/최종 저장 시각).

**전송**
- 주기: 30분마다 + VS Code 종료 시 + 명령 `WorkLog: 지금 전송`.
- 엔드포인트: `POST /api/vscode/sessions` (X-Api-Key).
- 같은 `(user, repo, branch, 날짜)` 세션은 서버에서 최신 내용으로 갱신(UPSERT).

**설정 (`settings.json`)**
```json
{
  "worklog.serverUrl": "http://localhost:8080",
  "worklog.apiKey": "wl_xxx",
  "worklog.intervalMinutes": 30,
  "worklog.collectDiff": true
}
```

**커밋 리마인드**: 서버는 미커밋 diff가 300줄 이상이거나 마지막 커밋이 6시간 이상 지난 세션을 감지하면 Mattermost로 리마인드(F7). 확장 자체에서는 상태바에 "미커밋 N파일" 표시만.

**수용 기준**
- 확장 설치 후 파일을 수정하고 `지금 전송`을 실행하면 대시보드 "진행 중 / 미커밋"에 나타난다.
- API Key가 틀리면 상태바에 오류 표시, 예외로 죽지 않는다.

### F7. Mattermost 알림 (P1, 담당자 2)

- 설정: 사용자별 또는 전역 Incoming Webhook URL.
- 이벤트
  1. 일지 초안 생성 완료 → "📝 {이름}의 {날짜} 업무 일지 초안이 생성되었습니다. {링크}" + 완료 작업 상위 3줄
  2. 미커밋 리마인드 → "⚠️ {repo}@{branch}에 미커밋 변경 {N}파일이 {H}시간째 있습니다."
  3. 초안 확정 시 채널에 전체 Markdown 게시 (사용자가 "Mattermost 전송" 버튼 클릭 시에만)
- `MattermostNotifier`는 `Notifier` 인터페이스 구현체. 전송 실패는 로그만 남기고 본 흐름을 막지 않는다.

### F8. 외부 API (P1, 담당자 2)

메신저 봇 등 외부 시스템이 API Key로 일지 데이터를 가져갈 수 있게 한다. §7의 조회 엔드포인트를 그대로 `X-Api-Key`로도 허용하면 충족. 추가로 요약 전용 엔드포인트:

- `GET /api/external/summary?date=2026-09-09` → 그날 전 사용자의 초안을 사용자별 5줄 요약으로 반환 (Mattermost 슬래시 커맨드 응답용).

## 10. E2E 검수 시나리오 (3일차 체크리스트)

1. GitHub 로그인 → `/repos`에서 리포 등록 → 수동 동기화 → 홈에 오늘 커밋 표시
2. 동기화 2회 반복 → 활동 건수 불변
3. 홈에서 "초안 생성" → 초안 편집 페이지 열림 → 내용 수정·저장 → 확정 → 상태 CONFIRMED
4. 확정된 초안이 있는 날짜에 재생성 → version 2 DRAFT 생성, 확정본 유지
5. VS Code에서 파일 수정 + 계획 메모 입력 + `지금 전송` → 홈 "미커밋 세션" 카드 증가, 초안 재생성 시 "진행 중 / 미커밋" 섹션에 반영
6. `/settings`에서 API Key 발급 → `curl -H "X-Api-Key" /api/external/summary?date=` 응답
7. 초안 "Mattermost 전송" → 채널에 Markdown 게시
8. `WORKLOG_LLM_PROVIDER`를 `gemma4` → `qwen3`로 바꿔 재시작 → 코드 수정 없이 요약 내용 변화, 기동 로그에 `/models` 검증 성공 표시
9. 잘못된 API Key로 확장 전송 → 401, 확장은 상태바 오류 표시만

## 11. 비기능 요구사항

- 로컬 `docker compose up` + `bootRun` + `npm run dev` 3개 명령으로 전체 구동.
- GitHub API rate limit(5,000/h) 고려: 커밋 상세는 신규 커밋만 조회, `If-None-Match` ETag 사용은 선택.
- LLM 호출은 비동기 큐(`@Async` + DB 상태 컬럼)로 처리해 API 응답을 막지 않는다.
- 비밀값(GitHub 토큰, LLM 키)은 평문 저장 금지.
- 백엔드 단위 테스트: `DraftGenerator`, `GitHubCollector` 파싱(고정 JSON fixture), `LlmProvider` 재시도 로직. 프론트는 빌드 통과 + 목업 렌더 스모크 테스트.

## 12. 확정된 가정 (더 이상 논의하지 않음)

아래 항목은 팀에서 현재 가정대로 진행하기로 확정했다. 바꾸려면 PRD를 먼저 고친다.

| 항목 | 확정 내용 |
|------|---------|
| 실제 LLM | 사내 로컬 LLM 2종: **gemma4**(`google/gemma-4-26b-a4b-qat`, 기본)와 **qwen3**(`qwen3.8:27b`). 둘 다 OpenAI 호환 API → `OpenAiCompatProvider` 하나 + 프리셋. 개발 중엔 `mock` |

| "로컬 AI"의 의미 | 백엔드가 위 사내 LLM 엔드포인트를 호출하는 것. 외부 상용 API·브라우저 내 추론은 하지 않음 |
| 일지 자동 생성 시각 | 매일 18:00 KST (`DRAFT_SCHEDULE_CRON`으로 변경 가능) |
| 미가입 커밋 author 처리 | `external_login`만 저장하고 초안 생성 대상에서 제외 |
| 사용자 간 초안 열람 권한 | 전원 조회 가능, 편집·확정은 본인만 |
